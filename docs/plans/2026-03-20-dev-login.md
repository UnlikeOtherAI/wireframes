# Dev Login

## Problem Statement

Local development currently depends on the external authenticator flow, which slows down basic UI and API work and makes local setup heavier than it needs to be. The admin login screen also only exposes the external path, even when a developer just needs a predictable local session.

## Current Behavior

- The admin login page only shows the authenticator sign-in button in [admin/src/features/LoginPage.tsx](/System/Volumes/Data/.internal/projects/Projects/wireframes/admin/src/features/LoginPage.tsx).
- The admin auth client expects auth responses shaped as `{ token, user }` in [admin/src/api/auth.ts](/System/Volumes/Data/.internal/projects/Projects/wireframes/admin/src/api/auth.ts).
- The API SSO callback currently returns only `{ token }` in [api/src/controllers/auth.ts](/System/Volumes/Data/.internal/projects/Projects/wireframes/api/src/controllers/auth.ts).
- API auth is documented as SSO-only in [docs/architecture.md](/System/Volumes/Data/.internal/projects/Projects/wireframes/docs/architecture.md).

## Desired Behavior

- The login screen keeps the authenticator button.
- When a dedicated environment variable enables dev auth, the login screen shows a second `Dev login` button underneath it.
- `Dev login` creates or reuses one default local user and one default local project, then signs the browser in without using the external authenticator.
- The authenticator login and dev login return the same response contract so the admin UI has one login path after the request returns.
- Dev auth is unavailable unless explicitly enabled.

## Design

- Add `DEV_AUTH_ENABLED` to the API config and `VITE_DEV_AUTH_ENABLED` to the admin env surface.
- Add a public `POST /auth/dev-login` route in the API.
- Keep layering intact:
  - Route: dispatch `POST /auth/dev-login`
  - Controller: validate dev auth availability and request locality, then call service
  - Service: ensure the default dev user exists, ensure the default dev project exists, and issue a JWT
  - Repository: provide any missing lookup/upsert helpers needed for the default user/project
- Update the existing SSO callback to return `{ token, user }` so both login buttons share the same admin-side flow.
- Update the admin login page to render the second button only when `VITE_DEV_AUTH_ENABLED === "true"` and to reuse the same local auth store/navigation flow after a successful response.

## Implementation Order

1. Normalize API auth responses so SSO returns `{ token, user }`.
2. Add env-gated dev-login route/controller/service/repository support in the API.
3. Add the conditional `Dev login` button and client call in the admin app.
4. Add/adjust API and admin tests for both response shape and gated UI behavior.
5. Update architecture docs to mention local dev auth as an environment-gated development-only path.

## Edge Cases

- `DEV_AUTH_ENABLED` is unset or false: `POST /auth/dev-login` returns 404 or 403 and the login page does not render the button.
- Repeated dev logins: the same default user and default project are reused instead of duplicating records.
- Remote deployment with the flag accidentally enabled: the controller should still reject non-local requests.
- Existing local data: dev login should not overwrite unrelated users or projects.

## Non-Goals

- Adding a full alternative auth provider.
- Introducing organizations or changing the current project/membership model.
- Adding configurable multi-user dev impersonation in this change.
